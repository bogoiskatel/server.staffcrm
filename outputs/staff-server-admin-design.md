# STAFF SERVER Адмінка на PHP 7 і MySQL

Специфікація першої версії для погодження. STAFF SERVER є незалежним сервісом у репозиторії `bogoiskatel/server.staffcrm`. Адміністратор входить за логіном і паролем, переглядає карту мережі, підсумкові показники та історію статистики окремої установки. Існуюча STAFF CRM не змінюється в межах цієї роботи.

## Стек і оформлення

PHP 7.4, MySQL, PDO з підготовленими SQL-запитами, серверні PHP-шаблони. База називається `server`, кодування utf8mb4. Оформлення наслідує оригінальну тему STAFF CRM: шапка, світлий фон, картки показників, кнопки, таблиці. Використовуються Bootstrap, DataTables і Leaflet; перед копіюванням файлів перевіряються ліцензії, зберігаються повідомлення про авторство. Приватні конфігурації та дані CRM не копіюються. Нові функції мають короткі англійські коментарі; інтерфейс підтримує UA/EN.

Рекомендовано один застосунок: сторінки адмінки, шар доступу до БД і окремі CLI-завдання збору. Окремий frontend/backend додає розгортання і не потрібен для описаного інтерфейсу. Docker залишається варіантом ізоляції середовища, а не обов’язковою частиною продукту.

## Вхід і конфігурація

`config.php` задає змінні підключення до MySQL, ім’я адміністратора, хеш пароля, часовий пояс і параметри карти. Пароль перевіряється через password_verify; хеш створюється окремою CLI-командою. Приклад конфігурації містить лише порожні значення та пояснення. Реальний config.php виключається з Git, а вебсервер обслуговує тільки каталог public.

Форма входу містить ім’я користувача та пароль. Після входу оновлюється ідентифікатор сесії. Cookie має HttpOnly, SameSite і Secure під HTTPS; локальний HTTP допускається лише в явно заданому локальному режимі. Для POST-запитів діє CSRF-захист; спроби входу обмежуються за часом і джерелом через БД. Вихід виконується POST-запитом і знищує сесію. Всі сторінки та JSON даних карти вимагають авторизації.

## Дашборд

Два таби: «Мережа» та «Статистика».

«Мережа»: зверху картки загальної кількості CRM, членів церкви, охрещених за звітний місяць і за рік, приєднаних і вибулих за рік, домашніх груп поточного сезону, людей на дисципліні. Нижче карта з маркерами установок. Popup містить назву церкви і посилання на її деталі. Позначка за поштовим індексом явно позначається як приблизна.

Дані підсумовуються для одного вибраного звітного періоду, без змішування різних місяців. Період і покриття збору показуються поруч: скільки CRM передали дані з кількості очікуваних. Для кожного показника враховуються лише відомі значення. Неповний підсумок позначається як неповний; якщо жодного значення немає, показується «Немає даних», а не 0. Відсутні знімки не замінюються даними попереднього місяця без явного позначення.

«Статистика»: DataTable з пошуком, сортуванням і пагінацією. Колонки: назва церкви, країна, поштовий індекс, дата реєстрації, останній успішний збір, стан збору, кількість членів за вибраний період. Назва веде на сторінку установки. Порожня база показує чесний порожній стан.

## Сторінка установки

Службові дані установки, карта її розташування, стан останнього збору та історія щомісячних знімків. Для кожного знімка показуються всі погоджені показники, reporting_period, generated_at і collected_at. Невідомі last_successful_login і статистичні значення зберігаються як NULL. Секрети й зашифровані payload не виводяться у HTML.

Контакт відповідальної людини позначається як непідтверджений. Його розшифрування виконується лише окремою дією адміністратора; номер не з’являється у відкритому реєстрі, карті, журналах чи Git.

## Структура MySQL

| Таблиця | Призначення |
| --- | --- |
| installations | Незмінний UUID, назва, canonical HTTPS API URL, ISO-код країни, телефонний код країни, поштовий індекс як рядок, передані координати церкви, координати для відображення, джерело координат, дата реєстрації, стан установки |
| installation_credentials | Зашифрований API-секрет і контактний номер, ідентифікатори ключів для ротації; ключі поза БД і Git |
| statistics_snapshots | UUID установки, reporting_period, generated_at, collected_at, nullable показники, версія контракту; UNIQUE(installation_id, reporting_period) |
| collection_attempts | Установка, період, час спроби, результат, безпечний код помилки; невдала спроба не перезаписує успішний знімок |
| geocoding_cache | ISO-країна, поштовий індекс, провайдер, координати, стан результату, час оновлення та допустимий строк кешування |
| login_attempts | Облік спроб входу для обмеження частоти, очищення за строком зберігання |

Міграції створюють структуру без видалення наявних даних. Статистичні лічильники невід’ємні, NULL відрізняється від 0. Тестові дані використовуються тільки в окремій тестовій БД, не в production server.

## Карта і резервне визначення координат

Первинне джерело — збережені координати поточної церкви CRM. Latitude перевіряється в межах −90…90, longitude −180…180; обидва мають бути числовими та скінченними. Значення 0 допустиме. Невалідна пара не створює маркер і фіксується як помилка даних.

Якщо координат немає, центр використовує перевірені ISO-країну та поштовий індекс для геокодування. Телефонний код не завжди однозначно визначає країну, тому за неоднозначності потрібен явний ISO-код. Індекс зберігається рядком із початковими нулями. Невизначені місця залишаються у списку без вигаданих маркерів.

Джерела координат: church_coordinates або postcode_geocoding. Результати геокодування кешуються й отримуються серверним завданням із лімітами та повторними спробами; відкриття дашборда не спричиняє масового геокодування. Зміна країни/індексу інвалідує відповідну прив’язку до кешу. Обчислені центром координати не записуються назад у CRM. Провайдер геокодування й тайлів обирається після перевірки офіційних правил конфіденційності, обмежень, кешування та атрибуції; до вибору провайдера геокодування не виконується.

## Межі API та реєстрації

Автоматична реєстрація запускається Майстром установки CRM. Умови встановлення пояснюють участь у мережі, агреговану статистику та передачу зашифрованого контактного номера, який центр може розшифрувати. Одноразовий код підтвердження номера у першій версії не використовується.

Payload шифрується відкритим ключем центру; приватний ключ є лише на STAFF SERVER. Шифрування саме по собі не підтверджує відправника. Підтвердження володіння endpoint і спосіб видачі API-секрету потребують окремого погодженого протоколу перед відкриттям реєстрації для зовнішніх установок. UUID є ключем реєстру. Людинозрозумілий токен CRM не використовується як секрет; оскільки він містить номер телефону, якщо його включено в контракт, він має передаватися та зберігатися як конфіденційне зашифроване поле.

Планований endpoint CRM — GET /api/v1/statistics. CRM обчислює показники, центр зберігає знімки. До контракту додається окремий nullable показник baptized_this_month: його не обчислюємо довільно з baptized_this_year. JSON також передає UUID, encrypted_api_url, поточні координати церкви, country/postcode та часові метадані. Зміни API та Майстра установки в існуючій CRM виконуються окремо; цей проєкт їх не редагує.

Collector запускається центральним CRON уночі першого числа, має незалежні результати по CRM, таймаути, повтори з backoff і рознесення запитів. Повторні спроби ідемпотентні. HTTPS URL проходять захист від SSRF, включно з перевіркою DNS/IP і redirect; внутрішні адреси не дозволяються.

Часовий пояс, трактування звітного місяця й календарного року та вимога точного знімка на опівночі ще не погоджені. Інтерфейс зберігає й показує період, який надійшов за контрактом; production-розклад collector не активується до погодження цих правил. Опитування після опівночі саме по собі не відтворює історичний стан на опівночі.

## Послідовність роботи і перевірка

Перший етап: схема MySQL, config.example.php, CLI створення хешу, вхід/вихід, дашборд із двома табами, карта відомих координат, DataTable і детальна сторінка. Без справжніх установок інтерфейс має порожній стан; синтетичні записи допускаються тільки для тестування.

Другий етап: погоджений приймач реєстрації, шифрування та перевірка endpoint, collector і геокодування після вибору провайдера та узгодження часу. Зовнішні інтеграції не підміняються автоматичним входом чи вигаданою статистикою.

Перевірки першого етапу: PHP 7.4 syntax, MySQL міграції в ізольованій БД, блокування доступу без сесії, правильний і неправильний пароль, CSRF та rate limit, вихід, збереження NULL і нулів, унікальність періодів, неповні підсумки, маркери з нульовими координатами, відсутні місця, екранування назв для захисту від XSS. Перевіряються сторінки в браузері, DataTable, таби і мобільний вигляд.

Код публікується в окремій гілці та PR у server.staffcrm. Реальні конфігурації, ключі, паролі, номери телефонів, дампи та тестові дані не публікуються.
